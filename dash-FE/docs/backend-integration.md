- **채팅**: 방 목록의 `lastMessageId / lastMessageContent / lastMessageAt / unreadCount`를 반영합니다. 최신 메시지가 화면에 보이고 문서가 전경일 때 `PATCH /api/chat-rooms/{roomId}/read-position`으로 읽음 위치를 갱신합니다. 실패 시 오류를 표시하고 재시도합니다. 상대방의 개별 메시지 읽음 여부는 추정하지 않습니다.

## 백엔드 담당자에게 우선 전달할 사항

1. **소개팅 상대 목록/추천 API가 필요합니다.** 신청 API는 `receiverId`를 받지만, 상대 회원 ID와 프로필을 조회할 API가 Swagger에 없습니다. 이 때문에 상대 탐색 → 신청을 실제 UI에서 완료할 수 없습니다. 목록/추천 기준, 페이지 방식, 상대 ID와 공개 프로필 필드, 빈 결과 조건을 확정해 주세요.
2. **군필 값의 의미를 확정해 주세요.** 제품 요구사항은 군필/미필 두 선택지입니다. 현재 enum은 `ACTIVE_DUTY / SOCIAL_SERVICE / NOT_SERVED / EXEMPT / NOT_APPLICABLE`입니다. 사용자 요청으로 임시로 **군필 → ACTIVE_DUTY**, **미필 → NOT_SERVED**, 여성 → NOT_APPLICABLE로 전송합니다. ACTIVE_DUTY가 현재 복무 중을 뜻한다면 군필과 다릅니다. 군필 전체를 나타내는 값 추가 또는 기존 값의 의미/변환 규칙을 명시해 주세요. 면제·사회복무 기존 데이터의 두 선택지 표시 기준도 필요합니다.
3. **미팅·소모임·리뷰·채팅 일정/신고 API가 Swagger에 없습니다.** 아래 표의 기능 지원 여부와 최종 계약을 알려 주세요. 경로는 현재 프론트에 남아 있는 예상 경로이며, 실제 서버의 확정 경로가 아닙니다.
4. **신청→수락→채팅 검증용 계정 2개가 필요합니다.** 각 계정은 이메일·학생 인증 및 프로필을 완료해야 합니다. 실사용자에게 테스트 신청/메시지를 보내지 않고 확인할 수 있는 테스트 상대 및 기회 초기화 방법을 제공해 주세요.

## 명세에서 추가 확인이 필요한 정책

- 이메일 재전송 대기 시간/인증번호 및 verificationToken 유효시간: UI는 기존 60초 대기를 사용합니다. 서버 정책 또는 응답 메타데이터/Retry-After를 알려 주세요.
- 학교 이메일 허용 범위: UI는 기존 요구대로 `@inha.edu`를 받습니다. 서버 스키마는 일반 email 형태만 기재합니다.
- 학생증 파일 용량 상한: JPEG/PNG와 413 응답은 명세에 있으나 정확한 상한은 없습니다. 업로드 상한 및 OCR 처리 예상 시간을 알려 주세요.
- 채팅 메시지 길이: 명세는 빈 문자열 금지만 있고 최대 길이는 없습니다. UI의 기존 2,000자 제한과 서버 제한 일치 여부를 확인해 주세요.
- 토큰 갱신/로그아웃/탈퇴/비밀번호 재설정 API는 없습니다. 현재 로그인 access token만 사용하고, 보호된 요청의 401에는 로컬 세션을 종료합니다. 로그아웃은 로컬 토큰 제거입니다.
- 채팅방 목록은 `id / roomType / name / createdAt`만 제공합니다. 상대 회원/참여자 정보, 최근 메시지, 미확인 수, 소개팅 requestId, 일정은 현재 응답에 없습니다. 필요한 필드를 확정해 주세요.
- 받은/보낸 신청 응답에는 만료시각이 없습니다. 프론트가 임의로 24시간 후 신청을 숨기던 동작은 제거했습니다. 만료 정책이 있다면 상태/만료시각을 명시해 주세요.
- 기회 정책은 최대 2회, 사용한 각 기회가 24시간 뒤 회복입니다. 별도 spend API는 없으며 신청 성공 시 서버에서 차감합니다.

## 검증 기록

- 실제 HTTPS 서버에서 OpenAPI 다운로드 성공. 서버 URL은 `https://dashtag.duckdns.org`로 확인.
- 로그인 POST에 대한 OPTIONS 요청에서 `Access-Control-Allow-Origin: http://localhost:5173` 확인.
- `npm test`: 18개 통과. 저장한 Swagger 명세와 mock 응답을 사용하는 API 계약/회귀 테스트. 실제 계정을 만들거나 서버 데이터를 변경하지 않습니다. 생년월일 형식 변환·자동 하이픈, 대문자 없는 비밀번호 요청도 포함합니다.
- `npm run build`: TypeScript 및 프로덕션 빌드 확인.
- `npm run lint`: 오류 0개 확인; 기존 경고는 별도 유지.
- 실서버 회원가입: 사용자가 이메일 인증·회원가입·학생 인증·프로필/이상형 저장을 완료했습니다. 에이전트가 저장 후 홈 화면 및 마이페이지에서 프로필·학과·이상형이 다시 조회되는 것을 확인했습니다.
- 실서버 조회: 홈에서 받은/보낸 요청 각 0건, 기회 2/2를 확인했고 채팅방 목록의 빈 상태도 확인했습니다.
- **실서버의 신규 신청→수락/거절→메시지 전송은 미검증입니다.** 상대 탐색 API 및 두 번째 인증 계정이 없어 실제 상대가 필요한 쓰기 검증은 수행하지 않았습니다. 계약 테스트 통과와 구분해야 합니다.

## 모바일 화면 및 가입 입력 개선

- 모바일 본문·전체 화면 시트·하단 팝업 폭을 공통 `--app-max-width: 430px`로 통일했습니다. 작은 화면에서는 화면 폭 100%를 사용합니다.
- 하단 주요 버튼은 기본 52px, 주요 닫기/뒤로 버튼은 44px 터치 영역입니다. 16~20px 좌우 여백과 safe-area를 적용했습니다.
- 회원가입의 기존 본문 390px / footer 520px 불일치를 제거했습니다. footer는 본문 흐름 안의 sticky 영역으로 변경했습니다.
- 미팅/소모임 상세 하단 영역은 화면 밖 fixed 폭 대신 해당 화면 내부의 flex 영역으로 변경했습니다. 지원 대기 상태의 원본 페이지는 코드상 공통 레이아웃을 적용했으며 실서버 데이터를 이용한 상세 화면 검증은 보류 상태입니다.
- 채팅 높이는 `100dvh` 및 공통 헤더/탭 높이를 사용합니다. 모달은 스크롤 가능한 최대 높이를 적용했습니다.
- 실제 브라우저 치수 측정: 320px 주요 화면의 가로 넘침 0, 프로필 수정 시트는 320/390/430px에서 본문과 폭 일치. 800px 화면에서는 본문/시트 모두 430px. 저장 버튼 높이 약 52px, 버튼 좌우 경계는 시트 내부입니다.
- 로그인/회원가입 시작 화면의 하단 버튼은 390~400px 실제 viewport에서 52px 높이 및 내부 여백 확인. 받은/보낸 대쉬·채팅·약관은 공통 모바일 폭 및 320px 레이아웃을 점검했습니다.
- 마지막 단계에서만 발견되던 생년월일 오류를 해당 단계에서 검사합니다. 숫자 8자리 입력 시 하이픈을 자동 삽입합니다. 닉네임·이름·MBTI·학과 등도 다음 단계 진입 전에 검증합니다.
- 비밀번호 필수 조건은 8~64자이며 대문자를 요구하지 않습니다. 조합 안내는 권장 사항입니다.
- 후반 브라우저 입력 제어가 지연되고 사용자 조작과 겹쳐, 자동 하이픈/오류 메시지의 최종 클릭 검증은 자동 회귀 테스트로 확인했습니다. 실제 모바일 키보드와 노치가 있는 물리 기기 테스트는 별도입니다.

## 실행

```sh
cd dash-FE
npm install
npm run dev
npm test
npm run build
npm run lint
```

포트 5173이 사용 중이면 Vite는 다른 포트로 우회하지 않고 실패합니다. `VITE_API_URL`로 서버 주소를 바꿀 수 있으며 기본값은 위 HTTPS 서버입니다. `tests/fixtures/openapi.json`은 이 점검 시점에 다운로드한 명세입니다.
